# AttritionIQ: Complete project blueprint

Build **AttritionIQ: An Explainable Employee Attrition Prediction & Workforce Analytics Platform**.

The goal is to make this look like a genuine HR analytics product, not a basic Streamlit application containing a CSV upload button and a prediction result.

Your application should demonstrate five things:

1. **Predictive ML:** Estimate the probability that an employee will leave.
2. **Explainable AI:** Explain which features influenced a prediction.
3. **Workforce analytics:** Discover patterns in historical employee attrition.
4. **What-if analysis:** Show how a prediction changes when input features change, without pretending those changes guarantee a different outcome.
5. **Model reliability:** Display real evaluation metrics, limitations, and warnings about prediction uncertainty.

We'll use your existing `HR_Employee_Data.csv` as the historical dataset. The application will also support predictions for manually entered employee profiles and, optionally, uploaded CSV files containing new employee records.

One important distinction: **the historical dataset is for learning and evaluation; new employee profiles are for inference.** We must not accidentally use the historical `left` column as an input when predicting new employees.

## 1. Technology stack

| Component | Technology | Purpose |
|---|---|---|
| Frontend | Streamlit | Interactive web application |
| Data processing | Pandas, NumPy | Cleaning and transformation |
| Machine learning | Scikit-learn | Training and evaluation |
| Advanced model | Gradient boosting | Benchmark a stronger predictive model |
| Explainable AI | SHAP | Explain individual predictions and global feature importance |
| Visualizations | Plotly | Interactive charts and dashboards |
| Model persistence | Joblib | Save the trained model pipeline |
| Testing | Pytest | Test preprocessing, predictions, and data validation |
| Configuration | Python environment variables and config files | Reproducible local setup |

**Recommended approach:** start with scikit-learn's Random Forest and HistGradientBoostingClassifier, alongside Logistic Regression as a baseline. Compare their actual results before selecting the final model. Add XGBoost only if its installation and performance justify the extra dependency.

You do not need deep learning or an LLM to make this project advanced. The important work is reliable evaluation, explainability, and a polished user experience.

## 3. Streamlit UI: what the user actually sees

The interface should look like a professional HR analytics SaaS dashboard. Use a dark navy sidebar, a clean light background, restrained accent colors, consistent typography, interactive charts, and clear risk indicators.

The application will have six main screens.

### Screen 1: Executive Workforce Overview

This is the landing page. It should answer: *What does our historical employee data tell us?*

**Top navigation:** AttritionIQ logo, Overview, Risk Analysis, Batch Predictions, Model Performance, What-If Lab.

**Top metric cards:**

| Card | What it displays |
|---|---|
| Total Employees | Number of records in the historical dataset |
| Historical Attrition Rate | Percentage with `left = 1` |
| Average Satisfaction | Mean satisfaction score |
| Average Monthly Hours | Mean monthly working hours |
| Model Recall | Recall measured on the held-out test set |

These must be calculated from the actual data. Model metrics should be displayed only after training and evaluation have completed successfully.

For your dataset, the initial historical figures are:

- **14,999** employee records.
- **3,571** employees labeled as having left.
- **23.81%** historical attrition rate.
- **11,428** employees labeled as having stayed.

The remaining cards, including model recall, should be calculated by the application.

**Charts below the cards:**

1. Attrition distribution: employees who stayed versus employees who left.
2. Department-wise attrition rate.
3. Attrition by salary category.
4. Satisfaction-level distribution.
5. Monthly hours versus attrition.
6. Years at company versus attrition.

Add filters for department, salary, and other relevant attributes.

**Innovative addition:** provide a short, automatically generated *Workforce Insights* section.

For example, the application could report:

> Employees in a particular salary category have a higher observed attrition rate than the overall dataset.

The actual category and percentage must come from the data. Do not hardcode findings or claim that an observed association proves causation.

### Screen 2: Individual Employee Risk Analysis

This is the core prediction interface.

The user enters an employee's information through a structured form.

**Employee profile form**

| Input | Example |
|---|---|
| Satisfaction level | 0.35 |
| Last evaluation | 0.80 |
| Number of projects | 5 |
| Average monthly hours | 260 |
| Time at company | 4 years |
| Work accident | No |
| Promotion in last five years | No |
| Department | Sales |
| Salary | Medium |

These are illustrative input values, not a claim about a real employee.

Include validation for allowed ranges and categories. The interface should explain whether percentage inputs expect values such as `35` or `0.35`, rather than silently interpreting them incorrectly.

The form has a **Predict Attrition Risk** button.

When the user submits it, the application runs the saved model pipeline and displays the actual output.

**Prediction result panel**

```text
EMPLOYEE ATTRITION ASSESSMENT

Estimated attrition probability
Calculated by the trained model

Risk category
Low / Medium / High

Prediction explanation
Top features influencing this prediction

Recommended review areas
Workload, satisfaction, career development

Model limitations
An estimate, not a guarantee
```

Use a probability gauge or horizontal bar, a clearly labeled risk category, and an explanation chart.

For instance, a model might estimate a 68% probability for a particular profile. That number must come from the fitted model, not from an example or manually assigned value.

Do not label the output as a guaranteed prediction or use an uncalibrated probability as if it were a reliable real-world likelihood.

**Innovative addition: Employee Risk Explanation**

Show the strongest contributing features using SHAP or another suitable explanation method.

For example, the interface could show that satisfaction and working hours contributed to the model's prediction.

Be precise: these are predictive associations, not proof that a particular factor caused an employee to leave.

### Screen 3: Batch Predictions

This feature makes the project more practical for real HR workflows.

Instead of entering employees one at a time, a user uploads a CSV containing multiple new employee profiles.

The application should:

1. Accept a CSV upload.
2. Validate the column names and data types.
3. Display invalid rows and explain the errors.
4. Allow the user to correct the file.
5. Generate predictions for valid rows.
6. Display a risk distribution and employee-level results.
7. Allow downloading the results as a CSV.

**Example results table**

| Employee | Estimated risk | Category | Explanation available |
|---|---:|---|---|
| Employee A | Calculated by model | Calculated | Yes |
| Employee B | Calculated by model | Calculated | Yes |
| Employee C | Calculated by model | Calculated | Yes |

These rows illustrate the interface. They are not actual predictions from your dataset.

For privacy, you should avoid collecting unnecessary personal information. Use anonymous employee references where possible.

**Important:** a new-employee prediction file should contain the required predictor columns, not the historical `left` target. If the uploaded file includes `left`, the application should not silently pass it to the model.

### Screen 4: Model Performance and Reliability

This is the screen that distinguishes a serious ML project from a demonstration that only looks attractive.

Display the actual results of your training and evaluation pipeline.

**Model comparison table**

| Metric | Logistic Regression | Random Forest | Gradient Boosting |
|---|---:|---:|---:|
| Accuracy | Measured | Measured | Measured |
| Precision | Measured | Measured | Measured |
| Recall | Measured | Measured | Measured |
| F1-score | Measured | Measured | Measured |
| ROC-AUC | Measured | Measured | Measured |
| PR-AUC | Measured | Measured | Measured |
| Calibration | Evaluated | Evaluated | Evaluated |

The application fills these values after training. Do not insert invented accuracy percentages.

Include the following visualizations:

- Confusion matrix.
- ROC curve.
- Precision-recall curve.
- Feature importance.
- Calibration curve.
- Training and evaluation dataset sizes.
- Selected decision threshold.

**A useful innovation: Model Reliability Panel**

Display warnings when:

- The input contains invalid values.
- The model encounters feature distributions unlike its training data.
- A prediction falls outside the model's validated operating conditions.
- The model has not yet been trained or evaluated.
- The evaluation sample is too small to support a confident conclusion.

These checks should be implemented explicitly. A model cannot reliably recognize every unfamiliar situation simply because it returns a probability.

Also display a warning if the model's performance changes substantially under group-based splitting, where identical feature profiles are kept together.

That is especially relevant to this dataset because repeated feature profiles could make ordinary random-split results look better than performance on genuinely different profiles.

### Screen 5: What-If Lab

This should be one of your most distinctive features.

Allow users to change selected employee attributes and compare model outputs.

For example:

- Original satisfaction: 0.35.
- Alternative satisfaction: 0.60.
- Original monthly hours: 260.
- Alternative monthly hours: 220.

The system evaluates both profiles and compares the outputs.

**Illustrative interface**

| Result | Original profile | Alternative profile |
|---|---:|---:|
| Satisfaction | 0.35 | 0.60 |
| Monthly hours | 260 | 220 |
| Estimated risk | Calculated | Calculated |
| Change in risk | Baseline | Calculated difference |

The interface might show that the model's estimated risk decreases for the alternative profile. The application must calculate the difference using the trained model.

Add a waterfall chart or a side-by-side comparison of the two profiles.

**Critical limitation:** this is a model-based scenario analysis, not proof that increasing satisfaction or reducing working hours will cause an employee to stay. Establishing causal effects requires stronger evidence and an appropriate study design.

### Screen 6: Data Quality and Model Audit

This is an additional feature I recommend because it makes the project more defensible in a technical interview.

Display:

- Number of records and columns.
- Missing-value counts.
- Duplicate-record and repeated-profile statistics.
- Target distribution.
- Invalid value counts.
- Percentage conversion status.
- Features used by the model.
- Features excluded from training.
- Training, validation, and test split sizes.
- Model version and training date.
- Evaluation dataset and limitations.

Include a downloadable data-quality report.

For your existing CSV, `Emp_Id` should be excluded from the predictors, while `left` should be used only as the historical target during training and evaluation.

This page demonstrates that you understand the complete data lifecycle, not just the prediction API.

## 4. Where does the actual data come from?

Use three distinct data flows.

```text
                    HISTORICAL DATA
                  HR_Employee_Data.csv
                           |

                    Data Validation
                           |
                           v
                     Preprocessing
                           |
                           v
                Stratified Data Splitting
                           |
               +-----------+-----------+
               |           |           |
               v           v           v
            Training   Validation     Test
               |           |           |
               v           v           |
          Model Fitting   Selection    |
               |           |           |
               +-----------+           |
                           |            |
                           v            v
                    Final Evaluation
                           |
                           v
                   Saved Model Pipeline
                           |
             +-------------+-------------+
             |             |             |
             v             v             v
        Single-Profile   Batch       What-If
         Prediction    Prediction    Analysis
```

The Streamlit interface reads the model outputs and evaluation artifacts generated by this pipeline.

### Data files

**1. `data/raw/HR_Employee_Data.csv`**

Your original historical dataset. Keep it unchanged as the source of truth.

**2. `data/processed/`**

Optional cleaned data and diagnostic outputs. These should be reproducible from the raw file.

**3. `data/sample/sample_new_employees.csv`**

A sample template showing the required input columns for new predictions.

Do not generate fake employee records and present them as actual company data. If you create synthetic examples to demonstrate the interface, label them clearly as synthetic.

**4. `artifacts/`**

Store the fitted model pipeline and any required preprocessing objects. Keep these generated artifacts out of version control unless there is a specific reason to publish them.

**5. `reports/`**

Store actual evaluation metrics, data-quality reports, and model metadata.

## 5. How to make it look like a real-world product

Use the following design principles.

| Element | Recommendation |
|---|---|
| Application name | AttritionIQ |
| Visual style | Modern HR analytics SaaS |
| Sidebar | Dark navy with clear navigation |
| Main background | Light neutral background |
| Metric cards | Compact cards with large values and small labels |
| Charts | Interactive Plotly charts |
| Risk visualization | Probability bar or gauge with an explicit label |
| Tables | Search, filtering, and downloadable results |
| Explanations | Feature contribution chart and concise text |
| Empty states | Explain what the user needs to do next |
| Errors | Display actionable validation messages |
| Responsive layout | Use Streamlit columns and containers carefully |

Avoid adding decorative AI chatbots, animations, or artificial scores simply to make the project appear advanced.

A polished dashboard with trustworthy model outputs is more valuable than a flashy interface with unreliable predictions.

### A particularly useful feature: Prediction Audit Trail

For every prediction, record non-sensitive audit information such as:

- Model version.
- Prediction timestamp.
- Input schema version.
- Estimated probability.
- Selected decision threshold.
- Whether validation warnings occurred.

Do not store identifiable employee details unnecessarily. Provide appropriate access controls and retention limits if this is deployed with real employee data.

## 7. Recommended development order

Do not attempt to build every feature simultaneously.

| Phase | Deliverable | Completion criteria |
|---|---|---|
| 1 | Dataset validation | Data types, target, ranges, and repeated profiles checked |
| 2 | Training pipeline | Reproducible model comparison |
| 3 | Model evaluation | Untouched test results and calibration analysis |
| 4 | Single prediction | Validated employee input returns a real model output |
| 5 | Streamlit dashboard | Overview and individual prediction pages |
| 6 | Explainability | Feature explanations for individual predictions |
| 7 | Batch prediction | Upload, validation, results, and CSV export |
| 8 | What-If Lab | Compare two profiles using the same trained model |
| 9 | Testing and documentation | Automated tests and complete README |
| 10 | Deployment | Public demo with suitable privacy and security safeguards |

**The first milestone is not the UI.** It is a reproducible model pipeline that produces honest evaluation results. Otherwise, you risk building an impressive interface around a model whose performance has not been established.

## 8. Final project scope

My recommendation is to deliver the following as your initial portfolio version:

**Core features**
- Historical workforce dashboard.
- Employee attrition probability prediction.
- Model comparison and performance evaluation.
- SHAP-based explanations.
- CSV batch predictions.
- What-if scenario analysis.
- Data quality and model audit page.

**Later enhancements**
- FastAPI prediction service.
- Model drift monitoring using newly available, appropriately labeled data.
- Authentication and role-based access control.
- Historical model version comparison.
- Time-based evaluation, once suitable dated data becomes available.

There is one limitation you should make explicit in your README: your current dataset has no timestamps or source documentation. Therefore, you cannot establish whether the features were recorded before an employee left, nor can you demonstrate prospective performance on future employees from this CSV alone.

That does not make the project useless. It makes careful validation part of the project.

**The finished result should be an end-to-end, explainable ML application that accepts real input data, computes genuine predictions, exposes its limitations, and lets another developer reproduce its evaluation.** That is the version worth showcasing on GitHub and discussing in a placement interview.
